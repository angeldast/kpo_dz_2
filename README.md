Консольный модуль учёта оценок студентов. Kotlin, DDD, Ports & Adapters, паттерны GoF. Без внешних библиотек (кроме `kotlin.test` для тестов).
## Запуск
```bash
gradle run                    # интерактивная консоль (help — список команд)
gradle run --args="--demo"    # сквозной сценарий из ТЗ
gradle test                   # юнит-тесты инвариантов и Domain Service
```
Нужны JDK 17+ и Gradle (или откройте папку в IntelliJ IDEA). Состояние хранится в памяти на время работы процесса; экспорт пишет файлы CSV/JSON.
Сквозной демо-сценарий: заводит двух студентов и три критерия → выставляет оценки → показывает отклонённые попытки нарушить правила (балл 12 из 5, несуществующий критерий, отрицательный балл) → исправляет и отменяет оценки → считает итог под тремя политиками → экспортирует `out/grades.csv` и `out/grades.json`.
## Архитектура: Ports and Adapters (облегчённая)

```
src/main/kotlin/pos/
├── domain/          ← центр: Entity, VO, инварианты, Domain Service, порты-репозитории
├── application/     ← сценарии (сервисы), порт экспорта, view-DTO, фасад
├── infrastructure/  ← адаптеры: in-memory репозитории, CSV/JSON экспорт, консоль, DI-контейнер
└── Main.kt          ← composition root: единственное место, где порты связываются с реализациями
```
Зависимости направлены внутрь:
```
infrastructure ──► application ──► domain
   (адаптеры)       (сценарии)     (ядро, ни от чего не зависит)
```
- `domain` не импортирует ничего из `application`/`infrastructure`: ни файлов, ни CSV, ни консоли.
- Порты хранения (`StudentRepository`, `RubricRepository`, `EvaluationRepository`) объявлены **в домене**, реализации — в инфраструктуре. Порт экспорта (`GradeExporter`) объявлен в `application`, потому что экспорт — сценарий приложения, а не правило предметной области.
- `ConsoleUi` общается только с `PosFacade` и получает простые view-объекты, а не доменные сущности.
- DI-контейнер (`DiContainer`) — маленький собственный: регистрация фабрик по типу, ленивые синглтоны. Весь граф собран в `buildContainer()` в `Main.kt`.
## Карта DDD
| Понятие | Где в коде | Комментарий |
|---|---|---|
| Ubiquitous Language | `Student`, `Criterion`, `Rubric` (рубрикатор), `Evaluation` (оценка), `FinalGrade` (итог), `Score`, `Weight` | Названия совпадают со словарём из ТЗ |
| Entity | `Student`, `Criterion`, `Evaluation`, `Rubric` | У каждой есть идентичность. `Evaluation` идентифицируется парой (студент, критерий) |
| Value Object | `Score`, `Weight`, `FinalGrade`, `StudentId`, `CriterionId` | Неизменяемые, равны по значению, сами проверяют допустимость значения |
| Агрегаты | `Rubric` (корень) → `Criterion`; `Student`; `Evaluation` | Подробнее ниже |
| Инварианты | см. ниже | Охраняются моделью, а не UI и не сервисами |
| Repository (порт) | `domain/Repositories.kt` | Реализации в `infrastructure/InMemoryRepositories.kt` |
| Domain Service | `FinalGradeCalculator` | Итог строится на рубрикаторе и оценках одновременно, поэтому не принадлежит одной сущности |
### Entity vs Value Object — пример
`Student` — Entity: если студент сменил имя, это тот же студент (`id` прежний). `Score(8.0)` — Value Object: две оценки по 8 баллов взаимозаменяемы, у балла нет собственной жизни, он неизменяем. Поэтому исправление оценки заменяет `Score` целиком (`Evaluation.reassess`), а не «правит число».
### Границы агрегатов
- **`Rubric`** — корень агрегата, владеет критериями. Через него проходят добавление и удаление критериев, значит, проверка уникальности названия и «критерий существует» живёт в одном месте.
- **`Evaluation`** — отдельный агрегат со ссылкой на `StudentId` и `CriterionId` (по идентификатору, не по объекту). Его не вкладывали в `Student`, иначе при каждом проставлении балла пришлось бы загружать и сохранять студента целиком, а оценок будет много.
- Консистентность между агрегатами (удаление критерия/студента → удаление его оценок) обеспечивают сервисы приложения (`RubricService.removeCriterion`, `StudentService.remove`).
### Инварианты
| Правило | Где охраняется |
|---|---|
| Балл не отрицателен и конечен | `Score.init` |
| Балл ≤ `max_score` критерия | `Criterion.scoreOf` (единственный способ получить `Score` для критерия) |
| Оценка только по критерию из рубрикатора | `Rubric.requireCriterion`, вызывается в `EvaluationFactory` и при исправлении |
| Вес > 0, `max_score` > 0, непустые названия | `Weight`, `Criterion.init`, `Student` |
| Названия критериев уникальны | `Rubric.addCriterion` |
| Одна оценка на пару (студент, критерий) | `EvaluationService.rate` и ключ в репозитории |
| Итог ∈ [0, 10] и согласован с текущими оценками | `FinalGrade.init`; итог не хранится, а **вычисляется** при каждом запросе |
| Оценку нельзя создать в обход проверок | `Evaluation` имеет `internal`-конструктор, создаётся через `EvaluationFactory` |
### Формула итога
`итог = Σ(вес × балл / max) / Σ(вес) × 10`
## Паттерны GoF
| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | **Factory** | `domain/EvaluationFactory.kt` | Оценку нельзя собрать «руками»: фабрика — единая точка, где проверяются принадлежность критерия рубрикатору и диапазон балла, и где проставляется дата из `Clock` (тестируемо) |
| Структурный | **Facade** | `application/PosFacade.kt` | Консоль не знает про четыре сервиса и порядок их вызова. Составной сценарий `studentCard` (студент + оценки + итог) собирается в одном месте, а не в командах UI |
| Структурный | **Decorator** | `RoundingPolicyDecorator` в `domain/Grading.kt` | Округление — «особенность подсчёта», ортогональная правилу. Оборачивает любую политику, без копирования формулы и без комбинаторного взрыва классов (`full-rounded`, `rated-rounded`…) |
| Поведенческий | **Strategy** | `GradingPolicy`: `FullRubricPolicy`, `RatedOnlyPolicy` | Правило подсчёта меняется (отсутствующая оценка = 0 или не учитывается), а Domain Service не трогаем. Выбор политики — аргумент команды `grades <политика>` |
| Поведенческий | **Template Method** | `FileGradeExporter` → `CsvGradeExporter`, `JsonGradeExporter` | Общий каркас экспорта (создать каталог → отрендерить → записать), различается только `render`. Новый формат — один маленький класс |
В каждой группе не болше двух паттернов. Каждый закрывает конкретную проблему, а не добавлен «для галочки».
## Консольные команды
`add-student`, `students`, `remove-student`, `add-criterion <название...> <max> <вес>`, `criteria`, `remove-criterion`, `rate`, `correct`, `cancel`, `evaluations`, `grade`, `grades [политика]`, `policies`, `export <csv|json> <файл> [политика]`, `demo`, `help`, `exit`.
Идентификаторы студентов и критериев печатаются в квадратных скобках.
## Тесты
`src/test/kotlin/pos/DomainTest.kt` (11 тестов): выход балла за границы, отрицательный балл, граничное значение, критерий вне рубрикатора, повторная проверка при исправлении, дубли критериев, вес ≤ 0, расчёт итога под обеими стратегиями, декоратор округления, граничные итоги 0 и 10.
## Что намеренно не сделано
- Постоянное хранилище: порты готовы, достаточно написать JSON/файловый адаптер и поменять одну строку в `Main.kt`.
- Изменение критерия: смена `max_score` при существующих оценках может нарушить инвариант диапазона — потребовала бы отдельной политики миграции.
- Несколько курсов, пересдачи, апелляции: ядро это допускает (новые агрегаты по ссылкам-идентификаторам), но в ТЗ «сейчас достаточно ядра».
